01 Résumé exécutif

BertinoMusicBlocs est une application Electron de composition musicale organisée autour d'un modèle de blocs (Verse, Chorus, Bridge, etc.) disposés sur des pistes dans une vue timeline horizontale. L'architecture choisie — tout dans un seul fichier HTML — est volontaire et cohérente avec sa cible (app desktop légère, sans bundler). Le code est lisible, bien commenté et structuré en sections nommées. La v1.0 est fonctionnelle et déployable.

Les points de vigilance prioritaires sont : la sur-utilisation de render() (appel complet du DOM à chaque micro-interaction), quelques vecteurs XSS dans l'export HTML statique, et un état de snapshot (S.versions) qui grossit sans mécanisme de restauration exposé à l'utilisateur.

02 Architecture

Pattern single-file

L'intégralité du rendu vit dans src/index.html (HTML + CSS inline + JS inline). Le process principal Electron est dans src/main.js, le bridge de sécurité dans src/preload.js. Pas de bundler, pas de framework, pas de module ES — choix intentionnel et documenté.

Flux de données

S{} ── État global ──────────────────
↓ mutation directe
render() ── innerHTML total de #tracks-inner
↓ buildTrackRow() → buildBlockChip()
DOM ── Re-attachement de tous les listeners

window.electronAPI ── contextBridge (preload.js)
↓ ipcRenderer.invoke()
ipcMain.handle() ── main.js : dialogs, fs, menu

Globals intentionnels

  • S — état complet de l'application (tracks, blocks, selectedBlockId, key, tempo…)
  • TID / BID — compteurs d'ID pour tracks et blocs
  • _dragType, _dragBlockId, _dragTrackId — état du drag en cours
  • _spalBlock, _spBlock — blocs actifs dans les deux palettes staff
  • staffNotes, fretDots — données embarquées dans les objets block

Flux IPC (Electron)

  • Renderer → Main : ipcRenderer.invoke('save-json'), 'open-json', 'export-html', 'import-midi'
  • Main → Renderer : webContents.send('menu-action', action), 'load-recent'
  • Le contextBridge n'expose que des wrappers tipés — pas de ipcRenderer brut dans le renderer. OK

Avantages

  • Zéro dépendance runtime
  • Portable : fonctionne en navigateur direct
  • Déboguable sans build step
  • contextBridge correctement utilisé
  • Guards if (window.electronAPI) partout
  • Pattern override dans wireElectron() propre

Inconvénients

  • Fichier > 3 700 lignes, navigation difficile
  • Pas de séparation CSS/JS — refactoring risqué
  • Pas de tests automatisés
  • Globals mutables sans protection
  • Aucun système de module / namespace
  • Duplication de logique (3× staff UI)

04 Audit performance

render() — appelé trop souvent Critique

La fonction render() (ligne 2046) fait un innerHTML complet de #tracks-inner, détruisant et recréant la totalité des noeuds DOM. Elle est appelée 20 fois dans le code, y compris pour des opérations légères :

  • Ligne 2694 : toggleMute() → mute d'un bloc = reconstruction complète
  • Ligne 2701 : quickDeleteBlock() → idem
  • Ligne 2864 : openBlockDetail() → ouvrir le panneau de droite = reconstruction
  • Ligne 2977 : closePanel() → fermer le panneau = reconstruction
  • Ligne 3207 : newProject() → acceptable
Impact : Sur un projet avec 10 pistes et 80 blocs, chaque mute force la création de ~800 éléments DOM + re-attachement de 62+ event listeners. Avec des pistes staff (génération SVG), le coût est multiplicatif. 
// Exemple : openBlockDetail() (ligne 2858) déclenche render() AVANT d'ouvrir le panel
// pour mettre à jour la sélection visuelle du chip.
// Solution ciblée : ajouter/retirer .selected sur le chip existant sans render()
function openBlockDetail(id) {
  // ...
  render()  // ← inutile si on cible uniquement le chip concerné
  // ...
}

Accumulation de listeners Moyen

Chaque appel à render() recrée les éléments DOM et y attache de nouveaux addEventListener. Comme les anciens éléments sont détruits, il n'y a pas de memory leak au sens strict — mais les listeners dans bindKeys() (ligne 3163) sont ajoutés sur document et ne sont jamais retirés. La fonction bindKeys() est appelée une seule fois dans init(), ce qui est correct. Pas de fuite détectée ici.

Bloat des snapshots Moyen

La fonction snapshotVersion() (ligne 2984) pousse JSON.stringify(S) entier dans S.versions[]. Pour un projet de taille moyenne (50 blocs), chaque snapshot fait ~20–50 Ko. En session longue avec 20 snapshots, S.versions peut dépasser 1 Mo en RAM — et est sérialisé dans le fichier .bmb à chaque sauvegarde. 

// Ligne 2985
S.versions.push({ v: S.version, state: JSON.stringify(S), at: Date.now() })
// Solution : limiter à 10 snapshots max ou ne stocker que le diff

getElementById — pas de cache Mineur

Le helper $(id) = document.getElementById(id) est appelé de façon répétée avec les mêmes ID dans des fonctions fréquemment invoquées (openBlockDetail appelle $('panel'), $('panel-body'), $('panel-footer'), etc.). Un cache de référence serait bénéfique pour les éléments statiques (panel, toast, ruler).

05 Audit qualité code

Code mort — uid() Moyen

La fonction uid(prefix) est définie ligne 1816 mais n'est appelée nulle part. Les IDs sont générés via 't' + TID++ et 'b' + BID++. La fonction peut être supprimée. 

// Ligne 1816 — dead code
function uid(prefix) { return prefix + '_' + Math.random().toString(36).slice(2,9) }
// Non utilisé : les IDs réels sont 't1', 't2', 'b1', 'b2'…

S.versions — write-only Moyen

S.versions est rempli par snapshotVersion() (ligne 2985) mais n'est jamais lu dans l'UI. Il n'y a ni bouton "Restaurer le snapshot v2", ni liste déroulante d'historique. La fonctionnalité est donc à moitié implémentée. La donnée est sérialisée dans le .bmb mais silencieusement ignorée au chargement (loadState() ne lit pas data.versions).

Duplication CSS gradients dans buildExportHTML() Moyen

Les 14 classes .bloc-* avec leurs gradients sont définies deux fois : une fois dans le CSS principal de index.html (lignes 269–284), et une seconde fois intégralement recopiées dans la chaîne template de buildExportHTML() (lignes 3137–3151). Toute modification d'une couleur nécessite deux mises à jour synchronisées. 

// Ligne 269 (CSS principal)
.bloc-intro { background: linear-gradient(135deg,#2563eb,#7c3aed); }

// Ligne 3137 (dans buildExportHTML — copie manuelle)
.bloc-intro{background:linear-gradient(135deg,#2563eb,#7c3aed)}
// Solution : extraire les gradients dans une constante JS partagée

Handlers inline onclick/onchange Moyen

26 handlers inline sont utilisés dans le HTML (lignes 1591, 1600, 1607–1608, 1613, 1617–1623, 1650, 1669, 1679–1680, 1690–1691, 1705). Ils créent un couplage fort entre le balisage et le JS, et font échouer toute CSP unsafe-inline future. 

<!-- Lignes 1591, 1600 — exemples de handlers inline -->
<select onchange="onKeyChange(this.value)">
<select onchange="S.timeSign=$('#time-select').value;toast('Time: '+S.timeSign)">
<!-- Le second est particulièrement problématique : logique métier inline -->

Escaping inconsistant dans l'export HTML Critique

Dans buildExportHTML(), b.name et b.chords (lignes 3116–3117) et t.name (ligne 3121) sont injectés directement dans le HTML généré sans passer par esc(). Si un utilisateur nomme un bloc <script>alert(1)</script>, le fichier HTML exporté exécutera ce script à l'ouverture. 

// Ligne 3116 — VULNÉRABLE
return `<div class="block-chip bloc-${b.type}" ...>
  ${def.icon} <strong>${b.name}</strong>   // ← pas de esc()
  ${b.chords ? `<br><small>${b.chords}</small>` : ''}  // ← pas de esc()
</div>`

// Ligne 3121 — VULNÉRABLE
<div class="track-label">${cfg.icon} ${t.name}</div>  // ← pas de esc()

// La fonction esc() existe (ligne 3215) et est utilisée ailleurs — incohérence

Triple implémentation de la saisie staff Mineur

La logique de saisie de notes (durée + accidentel + nom de note + append) est implémentée en trois endroits distincts :

  • buildCtxStaff() + staffAppend() — palette gauche fixe (lignes 3378–3474)
  • showStaffPalette() + spalAppend() — palette flottante (lignes 1859–1956)
  • showStaffPopup() + staffAppendToBlock() — popup clic droit (lignes 2576–2675)

Ces trois implémentations partagent la même logique mais ont des états séparés (_staffDur/_staffAcc, _spalDur/_spalAcc, _spDur/_spAcc) non synchronisés.

Mesure 0-based vs 1-based Mineur

Les mesures sont stockées en base 1 (block.measure = 1 pour la première mesure). Le calcul de position CSS est (block.measure - 1) * MEASURE_WIDTH. La règle est cohérente dans le rendu, mais le ruler est rendu en base 0 (String(m) pour m = 0..31 — ligne 2013), ce qui crée une discordance visuelle : le ruler affiche "0" à la première position alors que les blocs commencent à la mesure "1".

06 Audit sécurité

contextBridge OK

src/preload.js utilise correctement contextBridge.exposeInMainWorld. Seuls 4 channels IPC sont exposés, tous typés. L'objet ipcRenderer lui-même n'est pas accessible depuis le renderer. Pas de nodeIntegration: true nulle part. Aucun enableRemoteModule.

innerHTML et XSS potentiel Moyen

26 usages de .innerHTML = sont recensés. La plupart utilisent esc() pour les données utilisateur. Exceptions :

  • Ligne 3116–3117 : b.name et b.chords non échappés dans l'export HTML (XSS dans le fichier exporté)
  • Ligne 3121 : t.name non échappé dans l'export HTML
  • Ligne 2735 : btn.innerHTML = ${cfg.icon} ${cfg.name} — données provenant de constantes internes, non utilisateur — risque nul en pratique
  • Ligne 1804 : el() prend un paramètre inner assigné en innerHTML sans échappement — interne uniquement, mais pattern risqué si étendu
Portée du risque : Le XSS dans l'export HTML n'est pas exploitable dans l'app Electron elle-même (le fichier exporté est ouvert dans un navigateur séparé). En revanche, un utilisateur pourrait créer un projet malveillant et envoyer le fichier .html exporté à une victime. Risque modéré dans un contexte collaboratif.

CSP Moyen

Aucune Content Security Policy n'est définie via <meta http-equiv="Content-Security-Policy"> dans index.html. Les handlers onclick inline requièrent unsafe-inline, ce qui rendrait une CSP stricte incompatible avec l'état actuel du code. Electron 31 applique une CSP par défaut permissive.

De plus, la balise <link> vers Google Fonts (ligne 8) est une requête externe. Elle est bloquée par Electron en production (pas de réseau par défaut pour les fichiers locaux), ce qui est acceptable, mais elle échoue silencieusement en mode offline.

Validation du schéma à l'ouverture Mineur

loadState() (ligne 3069) ne valide pas la structure du JSON chargé. Un fichier malformé avec un champ tracks qui n'est pas un tableau provoquera une erreur silencieuse ou un état incohérent. Le commentaire indique "still try to load for forward-compat" mais aucune validation n'est faite. 

// Ligne 3070–3072 — validation absente
if (data.app && data.app !== 'BertinoMusicBlocs') {
  // still try to load for forward-compat  ← aucune action, commentaire mort
}
S.tracks = data.tracks || []  // data.tracks pourrait être un string ou un objet

ipcRenderer — canaux supplémentaires OK

L'exposition IPC est minimale. Les listeners onMenuAction et onLoadRecent utilisent ipcRenderer.on() sans removeListener — ce qui crée techniquement des listeners permanents, mais dans le contexte d'une application à fenêtre unique, c'est sans conséquence.

07 Audit stabilité

Collision de blocs — détection incomplète Critique

La détection de collision dans dropBlock() (lignes 2828–2833) ne vérifie que si le point de départ est occupé, pas si le bloc de 4 mesures chevauche un bloc existant. De plus, si toutes les positions suivantes sont occupées, le bloc est quand même placé en overlap (commentaire "allow overlap"). 

// Lignes 2828–2833
const occupied = S.blocks
  .filter(b => b.trackId === trackId)
  .map(b => b.measure)  // ← ne capture que le point de départ, pas la largeur
let m = measure
while (occupied.includes(m)) m++
if (m > MEASURES) m = measure  // fallback, allow overlap ← collision silencieuse
La détection correcte nécessite de vérifier les plages [b.measure, b.measure + b.measures - 1] pour chaque bloc existant, pas seulement b.measure.

_spalBlock peut devenir stale Moyen

La variable globale _spalBlock (ligne 1836) pointe vers un objet block. Si l'utilisateur supprime ce bloc via le bouton ✕ ou via le panneau de détail pendant que la palette staff flottante est ouverte, _spalBlock pointe vers un objet orphelin (non présent dans S.blocks). Les appels suivants à spalAppend() modifient un objet hors du state, sans effet visible puis sans erreur explicite. 

// Ligne 1943 — _spalBlock peut être orphelin
function spalAppend(noteName) {
  if (!_spalBlock) return  // guard insuffisant : vérifie null mais pas orphelin
  // ...
  _spalBlock.staffNotes = ...  // mutation d'un objet non dans S.blocks
}

refreshStaffChip — fallback render() Moyen

Dans refreshStaffChip() (ligne 2677), si le chip n'est pas trouvé dans le DOM, la fonction appelle render() complet : 

// Ligne 2677–2679
function refreshStaffChip(block) {
  const chip = document.querySelector(`.block-chip[data-block-id="${block.id}"]`)
  if (!chip) { render(); return }  // ← render() complet si chip absent
}

Ce cas se produit quand la piste est collapsed ou group-hidden. Un render() complet est alors déclenché depuis un handler de saisie de note — coûteux et inattendu.

normalizeTrackOrder — logique de rang discutable Mineur

normalizeTrackOrder() (ligne 2786) assigne le rang 0 aux pistes "free" (lyrics, fretboard), le rang 1 à "main" (structure), le rang 2 aux "sub", et le rang 3 à "staff". Cela signifie que les pistes Lyrics et Fretboard sont toujours placées avant Structure, quelle que soit la position choisie par l'utilisateur via drag-and-drop. L'utilisateur perd le contrôle de l'ordre des pistes libres par rapport à Structure.

Ruler — base 0 vs blocs base 1 Mineur

Le ruler (ligne 2013) affiche les mesures de "0" à "31", mais les blocs sont positionnés à partir de la mesure "1". La mesure "0" du ruler correspond visuellement à la position de départ de la mesure "1" des blocs. Confusion pour un développeur qui relit le code, et potentiellement pour l'utilisateur.

MIDI import — stub fonctionnel Mineur

L'import MIDI dans le renderer (showMidiImport() ligne 3696) reçoit les données base64 du fichier MIDI mais affiche seulement un toast "MIDI imported (simulation)". Les données ne sont pas parsées ni intégrées à l'état. C'est un placeholder — acceptable en v1.0 mais à documenter clairement dans l'UI.

09 Roadmap améliorations

1. Undo / Redo Impact élevé

Actuellement il n'existe pas de Ctrl+Z fonctionnel. Le menu Electron expose { role: 'undo' } (ligne 155 de main.js) qui utilise l'undo natif WebKit (utile uniquement pour les champs texte). Pour l'état de l'application, il faudrait un stack d'états immuables ou une approche Command Pattern.

Approche recommandée : stocker une copie JSON de {tracks, blocks} avant chaque mutation dans un tableau _history[] limité à 50 entrées. Undo = pop + loadState(). Coût : ~5 Ko par état, négligeable.

2. Mises à jour DOM ciblées Impact élevé

Remplacer les render() appelés pour des micro-changements par des updates DOM ciblées :

  • Mute : ajouter/retirer .muted sur le chip + mettre à jour le texte du bouton
  • Sélection : ajouter/retirer .selected sur les chips concernés
  • Move de bloc : mettre à jour style.left et style.width du chip

Gain estimé : réduction de 70% des reconstructions DOM en session normale.

3. Détection de collision complète Priorité haute

Implémenter une détection correcte des intervalles. Lors d'un drop ou d'un move, vérifier que la plage [targetMeasure, targetMeasure + block.measures - 1] n'intersecte aucun bloc existant sur la même piste. 

// Logique correcte
function isFreeRange(trackId, startMeasure, numMeasures, excludeBlockId) {
  return !S.blocks.some(b =>
    b.trackId === trackId &&
    b.id !== excludeBlockId &&
    b.measure < startMeasure + numMeasures &&
    b.measure + b.measures > startMeasure
  )
}

4. Import MIDI réel Impact moyen

La plomberie Electron est en place (main.js reçoit les bytes base64). Il faut un parser MIDI léger dans le renderer pour extraire les tempo events, time signature et notes, et créer automatiquement des blocs. Une librairie comme midi-parser-js (~10 Ko) peut être copiée inline pour respecter la contrainte "zero npm dependencies runtime".

5. Validation du schéma à l'ouverture Impact moyen

Ajouter une validation légère de data dans loadState() : vérification des types, des plages, et des références (un block.trackId qui pointe vers une track inexistante). Afficher une alerte structurée plutôt que de laisser l'app dans un état incohérent.

6. Résolution du ruler 0-based vs blocs 1-based

Soit afficher le ruler de 1 à 32, soit stocker les mesures en base 0 partout et afficher m+1 dans l'UI. La seconde approche est plus courante en programmation musicale (MIDI utilise la base 0).

7. Unification de la saisie staff

Fusionner les trois implémentations de saisie de notes staff en un seul module avec état partagé. Proposer une seule interaction (la palette flottante) et supprimer le popup clic droit ou l'équivalent dans la palette fixe.
